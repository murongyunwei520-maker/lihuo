## 调研：Roins-hub/dola-pool 是否适配离火（仅评估，未改任何代码）

- 结论：不建议引入其代码、不替换 doubao-bridge；它本质是另一套「豆包/dola 账号池 + 出片后端」，与现有账号池、doubao-bridge、图片/视频生成链路高度重复。若只需多一个视频来源，最多作为隔离环境里的外部 OpenAI 兼容上游做 PoC。

- 与项目硬约束冲突：dola-pool 核心卖点是自动选号 / 估算额度记账 / 失败换号 / 代理与浏览器指纹伪装，而 PROJECT_OVERVIEW / KNOWN_ISSUES 明确「不自动切换豆包账号、不伪造额度、不擅自消耗额度」。它默认 `DOUBAO_ALLOW_PAID=1`（自动确认付费额度）、`DOUBAO_AUTO_NO_WATERMARK=1`（自动关 AI 生成明水印），存在额度与 AIGC 标识合规风险。
- 账号态不兼容：dola-pool 用 Cookie 导入 + 纯 HTTP 逆向协议；本项目用 Edge CDP 已开窗口、一个号一个窗口。同批账号同时跑会互相顶号 / 触发风控。
- 若将来要接：本地 openai provider 走 `/v1/videos` + `GET /v1/videos/{id}` + `/content`（Bearer Key、`video_url`），接口形状接近，但有具体缺口：本地轮询 120×2.5s≈5 分钟，而对方建议 15 分钟上限；本地发 multipart `seconds/size/ratio/resolution_name/generate_audio/watermark/mode/image[]`，对方只认 `seconds/duration/size/ratio/resolution` 等且不支持参考视频/音频；模型与时长范围（dola 5/10/30s、豆包 4–15/30s）与本地 Schema 不一致；需设 `DOLA_PUBLIC_BASE`。改超时/重试前按 AGENTS.md 需先向用户确认。
- 安全要点（静态审读）：默认 admin/admin123；`DOLA_API_KEYS` 留空 = 客户接口免鉴权；CORS 默认 `*`；`/videos`、`/thumbs`、`/v/{id}` 无鉴权靠不可猜 task id；README 写 `DOLA_ADMIN_KEY` 而 API.md 说该变量当前不生效（文档自相矛盾）；Fernet 密钥与密文同目录且存 Google 账号密码+TOTP；curl|sudo bash、git clone main 无校验、面板一键更新可远程换代码；`extensions/dola30/`、`bdcaptcha.js`、`bdms-sdk.js` 授权不在 MIT 范围（2.7.0 曾移除译自 GPL-3.0 的代码）。做得较好的部分：media.py 有 SSRF 校验、管理员密码 PBKDF2+compare_digest、约 90 个 pytest + CI。

## 2026-11-11 修复豆包任务串行排队（改为真并发）
- 原因：doubao-bridge 里 MAX_JOBS_PER_ACCOUNT=1 + acquireAccountLock 账号级互斥，runJob 全程持锁 → 同账号任务全部排队；finish() 里只减不增，activeJobs/busy 实际一直是空/false。
- 改法：删掉账号锁，改成创建任务时占并发槽位（acquireJobSlot，默认 3，DOUBAO_MAX_PARALLEL 可调），满员直接 429 ACCOUNT_BUSY 不排队；槽位在 enqueue 的 finally 释放（幂等）；ensureViewer 用 ensureViewerOnce 合并，避免并发重复开窗；run-doubao 下载目录改成 downloads/manual/<jobId>/ 防并发同名覆盖。
- 并发下暴露的第二个问题：后台标签页里 Playwright 的 locator.click/press 等渲染帧超时（image 任务不受影响因为用坐标点击）。给 vendor/doubao-brain/dbb/src/site.mjs 打了两个离火补丁：injectPrompt 的点击降级为尽力而为（后面用 evaluate focus+execCommand 写入）、sendPrompt 的 press 失败回退 page.keyboard.press。
- 文本回答取正文：新增 readAnswerText，取回答里 div.relative.grid（剔除 select-none 的时间戳/猜你想问）。
- 画布批量生成加 web/src/lib/concurrency.ts 的 mapWithConcurrency，豆包模型按 DOUBAO_MAX_PARALLEL=3 分批，避免一次发十几条被 429。
- 实测：3 个文本任务同时 running，52-55s 全部成功且答案分别正确；2 个生图任务并行 49/67s 成功、md5 不同、各自独立目录；第 4 个并发请求 429 ACCOUNT_BUSY；全部结束后 running=0，新任务可立即提交。
