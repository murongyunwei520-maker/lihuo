## 决策 1：为什么不新开 Edge 窗口？

**决策**：严格使用 CDP 连接已有 viewer 窗口，一个账号一个窗口，绝不新开 Edge。

**原因**：
- Windows 上 Edge 157+ 全局单实例转发机制，新开进程会秒退
- 用户自己已经打开了豆包网页，登录态在已有窗口里
- 新开窗口需要重新登录，消耗用户精力
- 已验证：launchPersistentContext 在系统已有 Edge 运行时必然秒退

**禁止事项**：
- 不要尝试 spawn 新 Edge 窗口
- 不要 launchPersistentContext
- 不要自动关闭用户正在用的浏览器

## 决策 2：为什么不自动选账号？

**决策**：默认 manual 模式，必须用户手动选账号。auto 模式框架保留但禁用。

**原因**：
- 豆包没有额度查询接口，所有账号额度状态 = unknown
- 自动选号会因为看不到真实额度而乱选，可能超额消耗
- 用户对自己的账号有明确认知，手动选最可靠
- 自动切换账号会打断用户当前正在用的窗口

**错误处理**：
- auto 模式下所有账号额度 unknown → 返回 ACCOUNT_QUOTA_UNKNOWN 错误
- 不静默选号，不猜测额度

## 决策 3：为什么删除豆包专属节点？

**决策**：不做豆包专属图片/视频节点，合并到通用卡片的模型下拉里。

**原因**：
- 避免重复 UI：生图/视频参数大同小异，单独做一套节点维护成本高
- 用户使用习惯：一个卡片里选不同模型即可，不需要切换节点类型
- 减少节点数量：画布上节点越少越清爽

**保留**：豆包 Bridge、账号池等后端能力全部保留。

---

## 决策 4：为什么用 expectedArtifactKind 而不是猜？

**决策**：任务创建时必须显式传 expectedArtifactKind="image" 或 "video"。

**原因**：
- 之前靠中文字符串 "视频生成" 推断任务类型，不可靠
- 豆包网页上可能同时有参考图和视频，容易混淆
- 显式传参更清晰，调试也容易

**校验规则**：
- Bridge 校验字段合法性，非法值直接报错
- Runner 严格按字段提取产物，不猜

---

## 决策 5：为什么做媒体文件多重校验？

**决策**：下载完成后检查文件大小 + magic number + MIME + 扩展名一致性。

**原因**：
- 之前遇到过下载到 HTML 错误页的情况，文件看着有内容其实不是图片/视频
- magic number 是最可靠的文件类型判断方式
- 校验失败删除不完整文件，不写入成功目录

**禁止**：不允许错误文件被标记成功。

---

## 决策 6：为什么用 close 事件而不是 exit？

**决策**：子进程退出用 close 事件，不用 exit。

**原因**：
- Node.js ChildProcess 中，exit 触发时 stdout 流可能还没读完
- close 事件在所有 stdio 流关闭后才触发，确保最后一段 stdout 被读到
- 之前遇到过最后一行 JSON 没换行就退出，导致解析失败的问题

## 决策 7：模型参数 Schema 化的方向

**决策**：从全局硬编码参数逐步升级为 Schema 驱动的动态参数面板。

**原则**：
- 渐进式改造，不一次性替换所有面板
- 有 Schema 的模型用动态面板，没有的继续用旧面板
- 不删除旧参数字段，兼容旧节点
- 参数按 providerId + modelId 独立缓存，切换模型不串

**当前进度**：
- ✅ 类型定义完成
- ✅ DynamicParamsPanel 组件完成
- ❌ 尚未正式接入实际节点

## 决策 8：账号锁和任务队列

**决策**：同账号串行执行，不同账号并行。

**规则**：
- MAX_JOBS_PER_ACCOUNT = 1
- 同账号第二个任务进入 queued 状态
- 队列有容量限制
- 排队任务可取消、可超时
- busy 只反映真实运行状态

---

## 决策 9：任务取消机制

**现状**：前端取消只停轮询，后台任务继续运行。

**原因**：完整取消需要浏览器层面关闭标签页，实现复杂，暂未做。

**风险**：取消后任务还在跑，消耗额度。

---

## 决策 10：Bridge 任务持久化

**现状**：任务只保存在内存 Map，Bridge 重启后任务丢失。

**原因**：先做最小可用版本，持久化后续再加。

**影响**：Bridge 重启后，正在运行的任务状态丢失，前端轮询会失败。
